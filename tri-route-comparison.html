VoxCPM2 的三条推理路线：PyTorch、MLX、GGUF

同一台机器、同一份权重、同一段文本，把三条技术路线都跑通并接到同一个 Web 应用里。 结论不是「谁最强」，而是三条路各自赢在不同的指标上：MLX 赢在吞吐，GGUF 赢在首包与内存，PyTorch 赢在不用折腾。

一句话总结：如果你只想要一个引擎，选 MLX。如果你在意「点下去多久出声」和内存占用， GGUF 的首包比 MLX 快 37%、内存持平、音质更好——但它一旦开始流式播放就会因为生成慢于实时而出现断点， 所以它更适合「整段生成 + 一次性返回」，而不是边生成边听。

三条路线到底差在哪

三者的模型结构完全一致（BaseLM → ResidualLM → FSQ → LocDiT/CFM → AudioVAE），差别全在用什么把矩阵乘法喂给 GPU、 权重以什么精度存放、以及谁来实现这个 2.3B 的推理循环。

五个值得记住的发现

  1. GGUF 的首包最快，因为它没有「先跑完再解码」的包袱

    llama.cpp 的实现从一开始就是 patch 级流水：每生成 4 个 patch（160 ms 音频）就立刻解码并写出。 而 PyTorch 版要等自回归循环跑完才进 VAE，MLX 上游更是全文只有一个 yield。 本项目的 MLX 流式是后来自己拆出来重写的，才追到 528 ms。

    实测：GGUF 301–362 ms · MLX 528 ms · PyTorch 790–880 ms

  2. 但 GGUF 的流式是「假实时」——首包快，后劲不足

    每块音频 160 ms，但相邻两块到达间隔约 240 ms。这意味着浏览器每播完一块就要等 80 ms， 连续播放会出现规律性断点。它更适合「先拿首包做反馈、整段拿完再播」， 而不适合边生成边无缝播放。这是本次对比里唯一一条会直接影响体感的硬缺陷。

    实测分块到达：0.38 → 0.62 → 0.86 → 1.10 → 1.34 s，间隔 240 ms；音频 160 ms/块

  3. 在 Metal 上，8bit 量化对 GGUF 几乎不提速，和 MLX 的结论相反

    MLX 里 8bit 比 bf16 快 1.38 倍，因为 MLX 的量化 kernel 把反量化融进了矩阵乘。 GGUF 这边 Q8_0 反而略慢于 F16（1.40 vs 1.36），体积从 3.0 GB 降到 1.6 GB 却没换来速度—— 反量化的开销吃掉了带宽收益。所以选 GGUF 时，Q8_0 的价值是省内存，不是变快。

    CLI 冷进程：Q8_0+F16 RTF 1.40/1.46 · F16+F16 RTF 1.36/1.39 · 两者常驻均 3.26 GB

  4. 声学权重留在 F32 是纯亏

    Acoustic 用 F32 会多占 1.8 GB（5.06 vs 3.26 GB），RTF 却没有任何改善（1.41 vs 1.40）。 原因是瓶颈在 CFM 的 10 步迭代上，精度不改变迭代次数。默认就选 F16。

    实测：Q8_0+F32 峰值 5.06 GB / RTF 1.42 · Q8_0+F16 峰值 3.26 GB / RTF 1.40

  5. 音质上 GGUF 这一轮是三者最好的

    同一段话做 ASR 回环，GGUF 与 PyTorch 都是 0% 错误，MLX 的 8bit 把「流式」听成了「刘氏」， CER 5.71%。这与之前的结论一致：MLX 的误差集中在同音字上，属于 ASR 侧误识而非合成退化， 但在三者对比里仍然是 measurable 的差异。

    35 字中文，FunASR paraformer-zh 回环：PT 0% · MLX 5.71% · GGUF 0%

GGUF 这条路线是怎么落地的

社区里的 GGUF 方案指的是 llama.cpp-omni 这个 fork，它把 VoxCPM 系列（0.5B / 1.5 / 2） 用 C++ 重写进了 ggml，并自带 OpenAI 兼容的 llama-tts-server。四步走到可用：

1. 编译（Metal 后端）

# ggml/CMakeLists.txt 在 Apple 上默认开 Metal
cmake -B build-metal -S . -DCMAKE_BUILD_TYPE=Release \
      -DGGML_METAL=ON -DENABLE_COREML=OFF \
      -DLLAMA_BUILD_TESTS=OFF -DLLAMA_BUILD_EXAMPLES=OFF -DLLAMA_OPENSSL=OFF

cmake --build build-metal -j8 --target voxcpm2-cli llama-tts-server llama-quantize

三个目标分别是命令行、HTTP 服务和量化工具。整套编译只用到 Xcode 命令行工具，无需额外依赖。

2. 转换（PyTorch 权重 → GGUF）

python convert_voxcpm2_to_gguf.py \
  --model models/VoxCPM2/model.safetensors \
  --vae   models/VoxCPM2/audiovae.pth \
  --config models/VoxCPM2/config.json \
  --output gguf-models --dtype f32      # 量化必须先出 F32

转换器从 config.json 的 architecture 字段识别出 voxcpm2， 拆成两个文件：BaseLM（28 层、n_embd 2048、vocab 73448）与 Acoustic（ResLM 8 层 / LocEnc 12 层 / LocDiT 12 层 / FSQ dim 512）， 并把 AudioVAE 的 weight_norm 合并后写进 Acoustic。耗时约 13 秒。

3. 量化

./build-metal/bin/llama-quantize \
  gguf-models/VoxCPM2-BaseLM-F32.gguf \
  gguf-models/VoxCPM2-BaseLM-Q8_0.gguf Q8_0

# model size = 6188.07 MiB (32.00 BPW)  →  quant size = 1644.03 MiB (8.50 BPW)

4. 起服务并接进 Web 应用

./llama-tts-server \
  --voxcpm2-base-lm gguf-models/VoxCPM2-BaseLM-Q8_0.gguf \
  --voxcpm2-acoustic gguf-models/VoxCPM2-Acoustic-F16.gguf \
  --host 127.0.0.1 --port 8819

# OpenAI 兼容端点
POST /v1/audio/speech          # 整段 WAV
POST /v1/audio/speech/stream   # 44 字节 WAV 头 + 裸 PCM 分块
GET  /v1/audio/speech/models   # 模型是否就绪（含 sample_rate）

接入时有两个坑要处理：一是它的流式响应带 44 字节 WAV 头，得剥掉才能对齐另外两个引擎的裸 L16 口径； 二是 /health 恒返回 ok，不能用它判断就绪，得看 /models 是否返回非空列表。 主服务里的 engine 字段现在是三选一，GGUF 走 httpx 流式代理，结果照样落盘并写历史。

选型建议

场景建议理由
Web 交互（默认）MLX 8bit唯一 RTF < 1 的路线，流式不断点，加载 0.2–0.7 秒
极致首包 / 低内存GGUF Q8_0首包 331 ms，内存 3.27 GB 且长期完全稳定；接受整体慢 1.6 倍
批量离线合成MLX 8bit吞吐最高；GGUF 的 Q8_0 在此场景只剩内存优势
要给别人部署GGUF单二进制 + 两个权重文件，无 Python 推理依赖，最容易打包
不想引入新运行时PyTorch只要 torch 能跑就行，代价是 11.6 GB 内存
诚实说明三处局限： ① GGUF 的「流式慢于实时」是从分块到达间隔推算的，没有做人工听感评估； ② RTF 单次测量有 ±0.15 的波动（MPS 与 Metal 会互相抢 GPU），表里的区间比单值更可信； ③ GGUF 的 0.87 秒加载是在权重已被系统页缓存的前提下测的，冷盘会更久。
