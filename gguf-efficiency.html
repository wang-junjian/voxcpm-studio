GGUF 路线还能快多少：把「慢」拆到算子这一级

GGUF 路线卡在 RTF ≈ 1.3–1.5，一直归因于「llama.cpp 不如 MLX」。加完分段计时后发现， BaseLM 只占每帧的 2.4%，真正吃掉 70% 的是 AudioVAE 解码，而它的算力利用率只有约 1%。 这篇把每个 patch 的 238 ms 拆开，逐条证伪四个直觉假设，并给出一个已经落地的改动：RTF 降 20%+，首包不变。

调参调不到实时

建图、量化、im2col 精度、批量全都试过，都不是主因。再往下必须改 VAE 的算子实现，不是改配置。

地板 RTF ≈ 1.0（VAE 单独）

先明确口径：RTF = 生成耗时 ÷ 音频时长，大于 1 就是慢于实时。流式能播是因为首包几百毫秒给了缓冲， 但长文本一旦 RTF 持续大于 1，播放端迟早饿死。所以这里的每一个百分点都算数。

一个 patch 的 238 ms 花在哪

流式路径每 160 ms 音频会调用一次 decode_step（LM + 扩散）和一次 decode_patch_streaming（VAE）。 给两处加打点后，20 个 patch 的数据高度稳定，波动不到 3 ms：

流式口径，timesteps=10，20 个 patch 平均。VAE 内含 0.15 ms 建图 + 4.6 ms 显存分配 + 162 ms 计算 + 0.02 ms 读回； 「建图」几乎免费，这直接推翻了第一个直觉。

第一个反直觉之处：量化对这条路线几乎没有意义。 BaseLM 从 F16 换到 Q8_0 省了 1.9 GB 内存，但它在每帧里只占 5.8 ms。 之前观察到「Q8_0 在 Metal 上不提速」，真正的原因不是量化没生效，而是被量化加速的那部分根本不是瓶颈。

把 VAE 拆到 block 级

最有信息量的实验是把解码器逐段截断（VOXCPM2_VAE_UNTIL=n，只跑前 n 个 block 后直接输出）， 20 个 patch 一起解码，量出每个 block 的边际成本：

20 个 patch 整段解码的累计曲线做差分。序列越短，单位成本越高：block 1 要在 32 帧上跑 2048→1024 的转置卷积， block 5 在 3840 帧上跑 128→64，后者数据量更大却更便宜——因为 GPU 终于被喂饱了。

用权重形状反算 MAC，再除以实测时间，得到各区间的有效吞吐：12 → 24 GFLOP/s（序列越长越高）， 而 M2 Max 的 FP16 峰值在 10 TFLOPS 量级。也就是说这块 VAE 只用到 GPU 的 0.2%–2%。 CPU 对照更能说明问题：CFM 在 Metal 上快 6.3 倍，而 VAE 只快 2.4 倍（320 ms → 132 ms）。

日志里能直接看到元凶之一：kernel_conv_transpose_1d_f32_f32。转置卷积没有走 GEMM， 而是朴素 kernel —— 每个输出点自己在内层循环里遍历输入通道。六层转置卷积恰好是 block 1/2 成本最高的部分。

四个被证伪的直觉

  1. 「每帧重建 VAE 图，开销肯定很大」

    实测建图 0.15 ms、graph 分配器 4.6 ms。就算把整条图缓存下来，每帧也只省 2–3%。而 VAE compute 一项就是 162 ms。

    build=0.15 ms · alloc=4.6 ms · compute=162.0 ms · read=0.02 ms

  2. 「im2col 走 F32，矩阵乘落到了 f16×f32 慢路径」

    改成 F16 后日志确实从 mul_mm_f16_f32 变为 mul_mm_f16_f16，但耗时纹丝不动（162 vs 162 ms）。说明瓶颈不在矩阵乘的精度路径上。既然没有收益，默认值已回退成 F32，不拿精度换空气。

    CHUNK=4：F32 最大差 31 LSB / SNR 63.3 dB ← 保留 F32 后仍是这个量级

  3. 「批量放大就能摊薄开销」

    整段解码 4 / 8 / 20 / 32 个 patch，平均每个 patch 的成本恒定在 134–140 ms。开销不是固定值，而是严格正比于音频长度。所以「一次多解几帧」不会让总量下降，只能提高单位吞吐。

    138.4 → 136.1 → 133.9 → 139.6 ms / patch

  4. 「量化 BaseLM 到 Q8_0 能提速」

    BaseLM 在每帧里只占 5.8 ms（2.4%）。之前测到 Q8_0 与 F16 速度无差别，原因不是量化失效，而是它加速的那一段根本不影响总时长。Q8_0 的价值在于省 1.9 GB 内存，不在速度。

    BaseLM 5.8 ms ↔ 总 238 ms

已经落地的改动：攒批解码

VAE 的吞吐随序列长度上升（134 ms @ 32 patch vs 167 ms @ 1 patch），所以把连续几个 patch 塞进同一张图是有收益的。 改动只有一处：首块仍然单独解码（首包延迟完全不变），之后按 VOXCPM2_CHUNK_PATCHES 攒批。

长句 76 字，服务态，timesteps=10。首次测量 CHUNK=4 在 1.33–1.45 间波动（机器上还跑着 MLX 与 PyTorch 服务）， 所以给区间而不是单值；方向与量级在 CLI 与 HTTP 两种口径下一致。

为什么 2 是 0 LSB、4 就有 63 dB 的差别？ 数学上 VAE 是纯因果卷积，攒批不改变计算语义。差异来自 GEMM 在不同 M 下选了不同分块， 浮点累加顺序不同。63 dB 的 SNR 在语音上听不出来，ASR 回环的 CER 也仍是 0%。 如果要求严格可复现，用 GGUF_CHUNK_PATCHES=2，代价是收益从 20% 掉到 5%。

另一条省钱路：少走几步扩散

CFM 是每帧里第二大的开销，且对步数严格线性。降步数能直接换时间，但会动音质，所以要配 ASR 回环看：

可懂度全程没掉（CER 都是 0），但 RMS 从 0.119 掉到 0.070 —— 能量变弱、听感发闷是扩散步数不足的典型表现。 推荐 8：省 5.5%，波形指标几乎不动。6 步以下不建议做默认，除非你能接受音色变薄。

两项叠加（攒批 4 + 8 步），服务态实测短句 RTF 1.29、首包 283 ms，是本轮调参能到的位置。

再往前，就不是调参了

方向具体做什么预估收益代价
立刻可用攒批 4 + timesteps 8（已落地）RTF −20%~25%无，重启生效
低风险 micro-opt去掉 conv 后的 permute+cont 全量转置、合并 snake 的 repeat 与大张量加法5%~15%要改 VAE 布局约定，需逐层回归
根治把 6 层转置卷积从朴素 kernel 改成「相位分解 + GEMM」，MAC 不变但能吃满 tileVAE 2~3×要写新图逻辑与重排 op，工作量按周计
绕开VAE 交给 MLX（每帧约 40 ms），GGUF 只负责 LM + CFMRTF → 0.7跨引擎传 latent，架构变脏

为什么说根治能到 2–3 倍：MLX 路线整条链 RTF 0.69，其中 LM + CFM 与 GGUF 同量级（约 70 ms）， 反推它的 VAE 每帧只要 40 ms 左右。同一个模型、同一块 GPU，差 3–4 倍，差距全在算子实现上，不在模型。

诚实的结论：调参的天花板由 VAE 决定。攒批 + 降步数能把 RTF 从 1.6–1.8 压到 1.29 左右， 但要让长文本真正跑到实时线以内（RTF < 1），必须动 voxcpm2_audiovae.cpp 里的卷积实现。 在此之前，GGUF 更适合当「C++ 单进程、无 Python 依赖、内存省」的离线批量引擎，实时流式仍是 MLX 的主场。

复现方式

# 1. 分段计时（每帧拆到 LM / CFM / VAE，含 VAE 内部的 build/alloc/compute）
VOXCPM2_PROF=1 ./build-metal/bin/voxcpm2-cli -t "本地语音合成系统的响应速度。" \
    --stream --timesteps 10 gguf-models/VoxCPM2-BaseLM-Q8_0.gguf \
    gguf-models/VoxCPM2-Acoustic-F16.gguf

# 2. 逐 block 截断，量每个 decoder block 的边际成本
VOXCPM2_VAE_UNTIL=3 VOXCPM2_PROF=1 ./build-metal/bin/voxcpm2-cli -t "..." --steps 20 ...

# 3. 攒批对比（服务态只需改环境变量，首块始终单独出）
VOXCPM2_CHUNK_PATCHES=1|2|4 ./build-metal/bin/llama-tts-server --voxcpm2-base-lm ... --port 8819

# 4. 服务态首包 / RTF（自动绕过本机代理）
.venv/bin/python bench_live.py 8819 10

# 5. 可懂度回环
.venv/bin/python asr_one.py out.wav "参考文本"

改动文件：voxcpm2_runtime.cpp（分段打点、decode_patches_streaming 攒批、VOXCPM2_VAE_UNTIL）、 voxcpm2_audiovae.cpp（im2col 精度开关）、webapp/start.sh（GGUF_CHUNK_PATCHES 默认 4）。 打点默认关闭，只有在设了 VOXCPM2_PROF 时才走计时分支。

这份结论的边界

  • 数字来自 M2 Max + Metal。上独显或用 CUDA 时，转置卷积的相对成本会变，攒批的最优点也可能偏移（可以扫 2/4/8）。
  • RTF 在服务态有 ±8% 波动（同机还跑着 MLX 与 PyTorch 两个常驻引擎），所以给区间不给单值；所有对比都是同口径、同机器连续测。
  • CER 只能证明「可懂」，证明不了「好听」。timesteps 6/4 的 CER 虽是 0，RMS 已明显下滑，选型时别只看 CER。
  • block 级拆分靠截断实现，截断后 tail 仍会构建，所以前缀那 26.9 ms 含 final conv，不能当成单个 block 的成本。
