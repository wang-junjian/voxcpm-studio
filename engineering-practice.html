01 · 全程概览

三个阶段的目标并不一样，前一个阶段的方法套不到后一个阶段。最典型的错配是：定位性能问题靠的是把时间拆细，而判断「能不能用」只能靠听。前者做到了，后者一开始没做。

前三步是「同一个问题越挖越深」，后两步是「换个问题」。04 与 05 的触发点都不是指标，是两句口语描述——这一点决定了它们不可能被自动化指标提前发现。

02 · 先拆开，再优化

最初的判断很朴素：GGUF 慢是因为 llama.cpp 不如 MLX，而 llama.cpp 的强项是量化，所以把 BaseLM 从 F16 压到 Q8_0 应该能提速。这个推理链条每一环看起来都成立，唯一的问题是没人量过 BaseLM 到底占多少时间。

于是先不改代码，只在 runtime 里插了分段计时：voxcpm2_prof() 包住 LM 前向、CFM 采样、VAE 解码、residual+FSQ 四段，用 VOXCPM2_PROF=1 控制开关。第一次跑出来的数字直接把假设推翻了。

条形总长 900 px 对应 238 ms。最右两个色块加起来 35 px——它们是「量化能起作用」的全部空间，也就是 4%。

结论很干脆：BaseLM 只占 2.4%，Q8_0 在 Metal 上不提速是必然的。它真正的价值是省 1.9 GB 内存，不是提速。真正吃时间的是 AudioVAE 的 6 层转置卷积，而 ggml 的 Metal 后端对 CONV_TRANSPOSE_1D 用的是朴素 kernel，没走 GEMM。

四个被证伪的假设

定位过程中有四个看起来更「像原因」的假设，都实测掉了。这些否定结论比正面的发现更有用——它们挡住的是后续反复走回同一条路。

假设预期收益实测判读
每帧建图 + 分配开销大 复用 graph 可摊薄 建图+alloc ≈ 6 ms 只占 2–3%，改它没意义
im2col 输出改 F16 走 F16 GEMM 卷积类算子加速 162 ms → 162 ms mul_mm_f16_f32 确实变 f16_f16，但没变快
逐帧解码有固定开销，攒批可摊薄 整段解码单帧更便宜 134–140 ms/patch 恒定 4 / 8 / 20 / 32 patch 都一样，没有可摊薄项
量化位宽影响音质 F16 应明显好于 Q8_0 CER 均为 0% Acoustic 保持 F16 是出于风险，不是数据
有效算力的两种口径。按 VAE 实际算的 FLOP 折算，整条链路只有 12 GFLOP/s；把攒批后的 4 帧一起算，也才 24 GFLOP/s。M2 Max 的 FP16 峰值是 10 TFLOPS——利用率 0.2%–2%。这解释了为什么所有「结构层面」的优化都只能拿到十几个百分点：底下的 kernel 没喂饱，上面怎么排队都没用。

03 · 在不改算法的前提下拿到 27%

既然真正的瓶颈是转置卷积走朴素 kernel，正解是把它改写成「相位分解 + GEMM」，让 6 层卷积全部落到矩阵乘上。这个改动按周计，当轮做不完。于是选了另一条路：不改算子，只改调用方式——把多个 patch 拼成一批，喂进同一张 VAE 图。

关键约束是首包延迟不能变差。所以解码循环改成：第一块仍然单独出，之后每攒满 4 个 patch 再解一次。

上排 12 个格子代表 12 次逐帧解码；下排把后 11 个 patch 按 4 个一组，合并成 3 次。首格位置完全没动，所以首包延迟不变——变快的只有稳态部分。

怎么判断「快了但没变坏」

攒批改变了浮点累加顺序，输出必然不是逐位相同。所以需要一条能接受的边界，而不是「看起来一样」。

对比逐样本最大差SNRCER结论
CHUNK=2 vs 逐帧 0 LSB ∞ 0% 逐位一致
CHUNK=4 vs 逐帧 31 LSB 63.3 dB 0% 差异低于 16 bit 量化噪声

63 dB 这个数比 16 bit PCM 的理论信噪比（约 96 dB）低，但比任何可闻失真门槛高得多；41 字中文的 ASR 回环 CER 是 0%。所以接受。这里定下的判据后来救了一次场——第 04 节那个「声音小」的问题，用同一套 SNR 指标完全看不出来。

测音质时不能让生成被硬截断。第二轮比对一开始拿到 CER 30%，差点当成攒批引入的回归。实际是测试脚本写了 --steps 20，模型在 3.2 s 处被截停，而整句需要 5.1 s。stop predictor 必须让它自然收尾，否则测的是「半句话的识别率」。

04 · 第一次翻车：用户说「声音非常小」

优化上线后收到一句反馈：「你优化后的 GGUF 基本不太能用，声音非常小」。第一反应是攒批出了问题，但 CHUNK=1 与 CHUNK=4 的输出逐位相同（见上表），所以不是。

真正的原因是我的验证方法有盲区：只比对了两段音频的 SNR，没有看任何一段的绝对电平。SNR 是相对量，两段都很小的时候它依然很好看。补上 RMS 与峰值统计后，问题立刻现形——某些「文本 × 种子」组合整段退化成气声，RMS 只有正常值的 1/8。

同一段文本、同一引擎，只改扩散步数。10 步时落在盆地里，步数加到 30–40 才会回到正常电平——这条路走不通，因为 40 步意味着 4 倍延迟。

为什么不能「把音量放大」

最省事的办法是乘一个增益。实测否掉了：退化样本放大 9.2 倍后 RMS 追平正常样本，但 ASR 回环 CER 仍是 21.05%，而正常样本是 7.89%。声音小是症状，不是原因——扩散没收敛，波形里的语义就是坏的，放大只是把错误放大。

还有一个证据说明这个问题与优化无关：命中率在四个实现上分别是 PyTorch 0/16、GGUF Q8_0 1/16、GGUF F16 1/16、MLX 2/16。连参考实现都会命中，与量化位宽无关，是两个独立重实现共有的扩散收敛问题。

修法：判退化 + 换种子 + 响度归一

  1. 判退化：看绝对电平，不看信噪比

    每段生成后算 RMS 与峰值，低于 0.035 / 0.22 判为退化。这两个阈值来自正常样本与退化样本之间近 10 倍的间隔，取在中间偏保守的位置。

    DEGEN_RMS=0.035 · DEGEN_PEAK=0.22

  2. 换种子重生成，最多 3 次取最响

    退化是「文本 × 种子」的确定性结果，所以换种子必然能跳出盆地。前端默认 seed 固定为 42，这正好解释了用户为什么「重试也没用」——他每次重试的都是同一个种子。

    MAX_ATTEMPTS=3 · 响应里回传 attempts / tried / seed_used

  3. 响度归一到 RMS 0.10

    即使不退化，同一引擎不同文本的 RMS 也在 0.04–0.25 之间波动，听感忽大忽小。统一归一到 −20 dBFS，峰值上限 0.95 防削顶，增益区间 [0.25, 16]。

    TARGET_RMS=0.10 · PEAK_CEIL=0.95
修复后同一案例 CER 回到 7.89%，5 段文本 × 3 个引擎的 RMS 全部落在 0.100，三引擎输出电平一致。

05 · 第二次翻车：用户说「断断续续」

第二条反馈同样不是性能数字能发现的：「GGUF 打开流式播放，有断断续续地感觉，不流畅」。这时 GGUF 的 RTF 已经是 1.335，听起来「比实时慢一点」，似乎不该断供。但流式播放的约束不是平均速度，是任一时刻的累积量。

算一下就清楚了。74 字长句产出 12.96 s 音频，生成耗时 18.5 s，即 r = 0.70 音频秒/墙钟秒；而播放器恒按 1× 消耗。差值 0.30 积累 18.5 s，就是 5.5 s 的缺口。旧逻辑「收到第一块就播」，实测断供 20 次、累计静音 5.8 s。

两条线的斜率差就是问题本身。阴影区是「已经播掉、但还没生成出来」的部分——它必须由开播前的缓冲覆盖，否则中途必然空转。

所以前端不能「收到第一块就播」，得等缓冲够。开播条件写成一个不等式：

B ≥ (1 − r) · T + jitter

r      —— 实测合成速率（音频秒 / 墙钟秒），用第一块之后的数据实时估
T      —— 剩余待生成音频时长，由「字数 × 每字秒数」推算（实测 0.175 s/字）
jitter —— 抖动余量，取决于历史最大块间隔

// r ≥ 0.98 的引擎（MLX 1.39 / PyTorch 1.04）该项退化为 0.12 s，完全无感
引擎r开播时刻（74 字）断供用户感受
MLX 8bit1.390.58 s0即点即播
PyTorch fp321.040.88 s0几乎无感
GGUF（顺滑，默认）0.707.6 s0要等，但不断
GGUF（低延迟开关）0.700.35 s20 次 / 5.8 s原故障
余量必须按抖动算，不能按平均值算。第一版只用了 (1−r)·T 的平均值，实测仍然断供 2 次、共 358 ms。原因是末尾缓冲恰好耗尽，任何一次局部速率下探就直接变成缺口。最后取满推的 8.5 s 再乘 0.6，得到 7.6 s，才做到零断供。

7.6 s 不是可调参数，是物理下限。想 0.6 s 出声又不断供，以 GGUF 现在的 r 做不到——唯一的路是流式换 MLX。所以界面上给了「低延迟优先」开关，把选择权交回用户，并记住选择。

06 · 收口：31 GB 搬进 26 MB 的仓库

最后一步是把工作目录变成可交付的项目。原目录 31 GB，其中 99.9% 是可重建的权重与构建产物，所以策略是代码进 git、资产留在磁盘但不进 git，并在文档里写清重建步骤。

搬移时踩了一个必然踩的坑：六个目录用 mv 挪进新仓库（同一卷是原子 rename，秒完成），权重路径天然生效——因为代码里全是相对路径。但 GGUF 引擎直接起不来了：

dyld: Library not loaded: @rpath/libllama-common.0.dylib
  Reason: tried: '/旧路径/voxcpm2/llamacpp-omni/.../build-metal/bin/libllama-common.0.dylib' (no such file)

CMake 默认把构建目录的绝对路径写进 LC_RPATH，而二进制依赖的是 @rpath/... 这种相对形式。目录一搬，rpath 还指着旧位置，dyld 直接拒绝加载。修法有两种，选了后者：

改成新的绝对路径

立刻能跑，但下次搬还会坏，而且换个用户 clone 下来也一样坏。

  • 治标
  • 依赖「目录永不变」这个假设

改成 @loader_path

让 dylib 相对可执行文件自己解析。项目从此可以放在任意位置。

  • 治本
  • arm64 改过 Mach-O 必须重新 ad-hoc 签名

另外两处也写死了旧路径，但都不致命：.venv/bin/ 下 93 个 console script 的 shebang（服务用 .venv/bin/python 相对调用，所以只有 pip 这类入口受影响），以及 build-metal 下 573 个 cmake 文本文件（只影响增量编译，不影响运行）。

资产路径体积不进 git 的理由
GGUF 权重gguf-models/16 GB可从 PyTorch 权重转换 + 量化
MLX 权重mlxrun/models/7.6 GB公开源直接下载
PyTorch 权重models/VoxCPM2/4.6 GBModelScope 可拉
主环境 venv.venv/2.0 GB149 个包，有 lock 文件
MLX 环境 venvmlxrun/.venv/584 MB38 个包，独立于主环境
Metal 构建llamacpp-omni/304 MB源码 + patch + cmake 可重建

搬完的验证不只是「能启动」，而是三个引擎各发一次请求、比对输出电平：MLX 0.6 s 就绪、GGUF 0.1 s 加载完、PyTorch 103 s，RMS 全部 0.10，音频正常落盘。git status 只剩三个文档改动，31 GB 零跟踪。

07 · 六条可以搬走的方法

下面这些跟 TTS、跟 Apple Silicon 都没关系，换个项目仍然成立。

#做法如果没这么做会怎样
01 先打点，再优化。把总耗时拆到阶段甚至算子，再决定改哪里。 会花一周优化只占 2.4% 的 BaseLM，然后发现毫无变化。
02 把证伪写下来。「试过、没用、为什么」和「试过、有用」同等重要。 后来的自己（或同事）会把同样的假设再试一遍。
03 相对指标要有绝对指标的锚。SNR 必须配 RMS/峰值一起看。 SNR 63 dB 的「完美结果」，实际是两段都是气声。
04 先判断是结构问题还是参数问题。r < 1 是结构性的，调缓冲只是绕过。 会去调播放器 buffer、调调度优先级，全都治不好。
05 优化要给可接受性边界，而不是追求最优。63 dB + CER 0% 就够，不必等 GEMM 重写。 为了完美的算子级优化推迟两周，用户这两周都在听断续。
06 构建产物有隐形路径依赖。rpath / shebang / cmake 缓存，搬目录前先想到。 「只是 mv 一下」，然后 GGUF 起不来，排查半天。

08 · 走错的四步

这一节比上一节更值得看。四个错误里有三个是验证方法本身的错误，而不是实现错误——代码写对了，但我用错了指标去确认它对不对。

  1. 只比 SNR，不看绝对电平

    攒批的等价性验证做得很细（逐样本最大差、SNR、CER 全查），但查的全是相对量。结果是「优化没改变波形」这个结论正确，「输出可用」这个结论错误。用户的耳朵比我的指标先发现问题。

    教训：验证要覆盖「有没有变」和「本身对不对」两个维度

  2. 测音质时让生成被硬截断

    第二轮 CER 比对拿到 30%，第一反应是攒批引入回归。实际是测试脚本限制了 --steps 20，模型在 3.2 s 处被截停，而整句需要 5.1 s。测出来的 CER 是「半句话的识别率」。

    教训：测试脚本的约束要和被测对象的语义一致

  3. 在 im2col 上换精度换空气

    看到 VAE 里的卷积走 mul_mm_f16_f32，判断改成 F16 输入能走更快的 F16 GEMM。日志确认 kernel 确实变了（fh16_f16），耗时一模一样 162 ms。于是默认回退 F32——不为零收益承担精度风险。

    教训：kernel 名字变了 ≠ 变快了，必须实测

  4. 抖动余量只按平均值推

    缓冲闸门第一版用 (1−r)·T 的平均值，理论够、实测仍断供 2 次共 358 ms。因为末尾缓冲恰好耗尽，局部速率一次下探就成了缺口。加了按历史最大块间隔缩放的抖动项才归零。

    教训：消耗型资源的余量要按最坏情况算，不能按平均
一个反直觉的观察：两个真正影响使用的缺陷（声音小、断续）都不是自动指标发现的，而是用户用两句话描述的。而我的自检脚本有 12 个端到端断言、若干 SNR/CER 比对——它们全都通过了。指标能证明「没有回归」，证明不了「能用」；后者需要有人真的听一遍。

09 · 复现

所有数字都可以重跑。前两条是性能口径，第三条是退化扫描，第四条搬移后的完整性检查。

# 1. 服务态 RTF / 首包（三引擎）
python bench_live.py

# 2. 流式分块节奏：每块到达时刻与间隔

# 3. 低能量退化命中率（16 个种子）
python scan_degenerate.py --engine gguf --n 16
python scan_engines.py --n 16

# 4. 搬移后完整性：三引擎各合成一句，比对 RMS
for e in mlx gguf torch; do

    -H 'Content-Type: application/json' \
    -d "{\"text\":\"搬移后第一次测试\",\"engine\":\"$e\"}" | jq '.rms'
done
